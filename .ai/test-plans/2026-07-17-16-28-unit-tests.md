# Unit Test Plan: Environment Agent

## Overview

This plan identifies pure logic functions suitable for isolated unit testing in the DCM Environment Agent. Following strict BDD principles, we test **only** algorithmic behavior with no external dependencies — configuration parsing/validation, data structure operations (slot management, deny list), mathematical formulae (backoff), pattern matching (provider ID, topic name), state machine transitions (health), and structured data assembly (CloudEvents, RFC 7807 errors).

**Excluded from unit tests (covered by integration tests):**
- HTTP handler behavior (request/response lifecycle, middleware ordering)
- NATS/JetStream interaction (topic creation, consumer binding, ack/nack)
- REST client behavior (DCM registration calls, SP health poll calls)
- Persistence layer I/O (file read/write, corruption handling)
- Signal handling and graceful shutdown
- Logging output assertions (framework-mediated)

**Excluded by Caller-Trust Principle:**
- Validating that callers pass non-nil arguments where the type system prevents it
- Re-checking preconditions the router/framework already guarantees (e.g., method matching)

## 5. Retry Backoff Calculation

### UT-DCM-010: Exponential backoff formula without jitter

- **Validates AC:** AC-DCM-050
- **Component Under Test:** backoff calculator (deterministic component)
- **Given** `initialInterval=1s` and `maxInterval=5m`
- **When** calculating backoff for attempt 0
- **Then** the calculated interval (before jitter) MUST be `min(1s × 2^0, 5m) = 1s`
- **When** calculating for attempt 3
- **Then** the calculated interval MUST be `min(1s × 2^3, 5m) = 8s`

#### Boundary Cases
- UT-DCM-011: Attempt 0 → `1s` (no multiplication)
- UT-DCM-012: Attempt 1 → `2s`
- UT-DCM-013: Attempt 9 → `min(512s, 300s) = 300s` (capped at max)
- UT-DCM-014: Attempt 20 → still capped at `300s` (overflow-safe)
- UT-DCM-015: Attempt 1,000,000 against a small (5m) max → still capped at `300s` and terminates immediately (no `O(attempt)` hang) — but on its own doesn't exercise the overflow guard near its actual int64 boundary, since `d` exceeds `max` within a handful of doublings regardless of how large `attempt` is; see UT-DCM-016/017
- UT-DCM-016: Zero `initial` → returns `max` directly, without entering the doubling loop
- UT-DCM-016b: Negative `initial` → returns `max` directly, same as UT-DCM-016 (separate entry since a negative duration is a distinct boundary from zero)
- UT-DCM-017: Attempt 1,000 against `max = math.MaxInt64` → the `d > max/2` overflow guard must fire at exactly the doubling where `d` first exceeds `max/2` (`2^62`, since `max/2 = 2^62-1`), returning `max` without `d` ever overflowing int64. `max = math.MaxInt64` specifically (not merely "large") is required for this test to actually discriminate the guard's presence: with a smaller cap (e.g. `MaxInt64/2`, tried and rejected during review), the next doubling after the guard would still fit in int64, so deleting the guard entirely produces the identical return value — verified directly by running both variants, and by mutation-testing (temporarily deleting the guard in `backoff.go` and confirming this specific test then fails)

### UT-MSG-080: onSetupReady fires exactly once, after JetStream is ready, before live consumption begins

- **Validates AC:** AC-RCM-047
- **Component Under Test:** `messaging.Client.setupStreamsAndConsume`, `messaging.Client.SetOnSetupReady`
- **Given** `DeferConsume: true` and an `onSetupReady` callback registered via `SetOnSetupReady`
- **When** `setupStreamsAndConsume` reaches the point where `c.js`/`c.mainCons`/`c.cancelCons` have
  just been populated for the first time
- **Then** the callback MUST fire exactly once, with `c.js`/`c.mainCons`/`c.cancelCons` already
  non-nil and `c.consuming` still `false`
- **And** calling `StartConsuming()` from within the callback MUST start exactly one live consume
  loop per topic (main, cancel)
- **Regression for:** a HIGH-severity finding — the composition root
  previously called `retry.Processor.ProcessOnRestart` synchronously right after
  `messaging.Client.Start` returned, assuming JetStream was already set up. `Start` is documented
  as non-blocking (AC-MSG-050): if NATS wasn't yet connected at that instant,
  `fetchAllFromConsumer` would silently return `(nil, nil)` on a nil JetStream context, and since
  `ProcessOnRestart` is invoked exactly once at startup with no retry of its own, restart-drain of
  the retry/cancel backlog would be permanently skipped for that startup. `onSetupReady` now fires
  from the one place JetStream readiness is actually known, regardless of whether that happens
  synchronously (NATS already reachable) or asynchronously (via a later `ReconnectHandler`-driven

### UT-MSG-090: beginConsuming is concurrency-safe under overlapping callers

- **Validates AC:** AC-RCM-047
- **Component Under Test:** `messaging.Client.beginConsuming`
- **Given** durable main/cancel consumers already set on the client
- **When** many goroutines call `beginConsuming()` concurrently, released simultaneously via a
  shared start barrier (repeated across many trials to defeat scheduling luck)
- **Then** exactly one goroutine's call MUST invoke `Consume()` on each of the main and cancel
  consumers — `c.consumers` MUST end up with exactly 2 entries, never more
- **Regression for:** a MEDIUM-severity finding — the previous
  `beginConsuming` released `c.mu` between reading the `consuming` guard and setting it back to
  `true` after starting the live consume loops, so two overlapping callers could both pass the
  "not yet consuming" check and each start a duplicate consume loop on the same durable consumer
  (double-processing messages). `beginConsuming` now holds `c.mu` for the entire
  check-then-act-then-mark sequence

### UT-MSG-095: finishSetup does not report success when beginConsuming fails after the onSetupReady callback runs

- **Validates AC:** AC-RCM-047
- **Component Under Test:** `messaging.Client.finishSetup`
- **Given** `DeferConsume: true`, an `onSetupReady` callback that synchronously calls
  `StartConsuming()` (mirroring `main.go`'s real callback shape), and a main consumer whose
  `Consume()` call fails with a transient error
- **When** `finishSetup` is called
- **Then** it MUST return `false` — NOT report success — even though the callback itself ran to
  completion, because `StartConsuming`'s own `beginConsuming()` call failed to actually start
  consuming
- **And** once the transient failure clears and `finishSetup` is called again (simulating a
  retry), it MUST succeed and begin consuming, without invoking `onSetupReady` a second time
  (`consumeRequested` is already latched true, so the retry takes the plain `beginConsuming`
  branch)
- **Regression for:** a HIGH-severity finding — `finishSetup`
  (`setupStreamsAndConsume`'s onSetupReady branch, before this fix) unconditionally returned
  `true` once the callback returned, regardless of whether `StartConsuming()` actually succeeded.
  Since the caller (`attemptSetup`) latches `setupDone` on a `true` return, and `setupDone`
  permanently short-circuits all future setup attempts, a transient `Consume()` failure right
  after (re)connect would silently and permanently strand the client "connected but not
  consuming" until process restart — no future reconnect or background retry would ever call
  `beginConsuming` again. See DD-420.
